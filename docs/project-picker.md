# Project picker

**`functions/project.zsh`** — interactive git project picker. Source this to get `project` and `current-project`.

- `project [query]` — opens an fzf picker over all git repos found under `$PROJECT_ROOTS`. Key bindings: `enter` focuses or opens the project, `ctrl-t` opens in a new kitty tab, `ctrl-i` opens the IDE, `ctrl-w` closes the project IDE, `ctrl-y` copies the path. Projects with open kitty windows are shown first (prefixed with `*`) in an _Open_ group; the rest appear under _All_. Preview pane shows open kitty windows then README/CLAUDE.md/ls.
- `current-project` — prints the git root of `$PWD`.
- `_project_build_list` — builds the tab-delimited `PATH<TAB>LABEL` list (with group headers) fed to fzf. Open projects detected from kitty CWDs. Both groups are ranked by zoxide frecency (third arg, from `_project_zoxide_scores`; highest first, ties and never-visited repos alphabetical by label) — see "zoxide ranking" below.
- `_project_zoxide_scores` — runs `zoxide query --list --score` and emits `SCORE<TAB>DIR<TAB>KIND` per entry, where `KIND` is `repo` (has a `.git` dir), `wt:<main>` (linked worktree, main repo resolved from its `.git` file's `gitdir: <main>/.git/worktrees/<name>`), or empty (plain dir, submodule). No output if zoxide isn't installed, which leaves the list alphabetical.
- `_project_preview_dir` — preview command: shows open kitty windows for the project (bold, with divider), then README/CLAUDE.md rendered by `glow` (`-s dark`, wrapped to the pane; `bat` if `glow` is missing) or `ls`.
- `_project_preview_windows` — reads pre-fetched `kitty @ ls` JSON from a temp file, returns bold-formatted window list for a given project path.
- `_project_picker` — runs fzf with all bindings; pre-fetches `kitty @ ls` once at startup into a temp file to avoid hangs in preview subprocesses.
- `_project_scan` — scans `$PROJECT_ROOTS` for git repos using `fd`, writes to cache file.

When run from a kitty key binding (no tty), `project` launches a new kitty tab for the picker and returns the result via a named FIFO.

**`bin/switch-project`** — intended to be bound to a kitty key binding (`launch --type=overlay`). Switches to `stack` layout for full-screen display, runs `project --new-tab-key`, then restores the previous layout via `kitten @ last-used-layout`. Focuses the matching kitty window by CWD, or opens a new window/tab. `ctrl-t` (new-tab mode) goes through `_project_open_in_tab` in `project.zsh`: the project's tab is found by title with kitty 0.50's `--focus-existing=@title` and created with `--location=by-title`, so project tabs are kept in alphabetical order; a window already open in the project is moved there with `detach-window --target-tab=@title --create-if-missing`. Design: `docs/superpowers/specs/2026-11-04-named-tabs-and-hunk-dock-design.md`.

**`bin/window`** — `fzf` picker over all open kitty windows; focuses the selected one. Switches to `stack` layout for full-screen display and restores the previous layout on exit. Preview pane shows the live screen content of the highlighted window via `kitty @ get-text --extent=screen --ansi`, with trailing spaces and SGR codes stripped by `perl`. Requires `listen_on` in `kitty.conf` so that `KITTY_LISTEN_ON` is inherited by fzf preview subprocesses (tty-based remote control blocks in subprocesses). Key binding: `ctrl-t` moves the selected window to its project's tab (named, alphabetical; made if missing — `_project_open_in_tab`). Its window list (`bin/window-list`) leads each row with what the window is running, since that is what tells windows apart: a one-character agent-state marker (red `!` blocked, yellow `…` working, green `✓` done and unseen, blank for an idle one or a window not running `claude`; legend in the fzf header) — see "Claude session state" below — then a `claude` window's Claude Code conversation title (e.g. `Window switcher fzf colors`) in the same faded grey as the vertical tab bar's lines — see "Claude session names" below — or, for any other window, its foreground process, dimmed (`zsh`). The project (the cwd's basename) follows, dimmed, the names padded so the projects line up (names up to 48 columns; a longer one pushes its own project out). A row ends in 🔔 if its window has rung a bell you haven't seen (`needs_attention` in `kitty @ ls`) — the tab bar's bell says only which tab. A row keeps its project even when it only repeats the name of the tab it's in, so that typing a project's name matches every window in it; `enter` on a tab header goes to its tab (`kitty @ focus-tab`). The tab isn't on the row. Rows stay in kitty's order whatever their state, which keeps each tab's windows together, and each tab gets a header row above its windows, which are indented under it: the tab's name, flush left, then a dim rule out to where the widest row ends (`project-tools ─────────`; a tab titled with a path — kitty's default is the active window's title, often its cwd — is cut to the last component). `bin/window` gives fzf `--delimiter '\t'` for this: its default, any whitespace, would count a row's indent as part of the gap after the id and drop it (which is how the blank marker of a non-`claude` window used to be lost, pulling that row two columns left of the rest). A header row's id is `tab:<tab id>` where a window's is its number; fzf can't skip a row, so the cursor does land on headers, but `ctrl-t` and `ctrl-w` do nothing there (`enter` goes to the tab, above), and the picker never starts on one (it opens on the window you came from, else the first window, `load:pos(2)`). `bin/window` runs fzf with `--layout=reverse-list`, so the list reads top to bottom in the tab bar's order, from the top of the screen, and `window-list` emits each header *before* its tab's windows (fzf's default bottom-up layout needed it the other way round, and showed the tabs and each tab's windows reversed; the prompt and header stay at the bottom, by your hands). A window closed with `ctrl-w` stays in place as a dimmed `[closed]` row, under its header even when that was the tab's last window (`closed_entries` records the tab along with the label).

**`bin/save-session`** — run by hand before quitting kitty or restarting the machine (with `restore_session_after_logout yes` in `kitty.conf`, kitty also saves everything itself on logout, restart or shutdown and restores it once at the next start in place of `startup_session`: scrollback and geometry come back, but only the shell is restarted, so agents are bare shells, not resumed — `save-session` and quitting kitty yourself is still how you get them resumed): writes every open window to a kitty session file (default `~/.config/kitty/sessions/restore.kitty-session`; point `startup_session` at it to restore). kitty's own `save_as_session` action (`kitty @ action save_as_session --save-only`) writes the tabs, layouts and working directories; `save-session` then makes each window running `claude` resume its own conversation. kitty records a window's id on its `launch` line (`'kitty-unserialize-data={"id": 12}'`), which joins to `kitty @ ls` and from there, by the claude process's pid, to `sessions/<pid>.json`'s `sessionId` (see "Claude session names" below); the id's JSON gains `"cmd_at_shell_startup": "claude --resume <sessionId>"`, which the restored window's shell runs on starting, through kitty's shell integration — run in the restored interactive shell with `eval`, but inside a function that has turned aliases off (`emulate -L zsh -o no_aliases`), so the command is wrapped as `setopt aliases; eval "…"`: the inner `eval` is parsed after the option is back on. That first-prompt moment is also before a prompt with an instant mode (Powerlevel10k's instant prompt) has given the shell its terminal back — output still goes to a file, where `claude` would run as a script and fail with "Provide a prompt to continue the conversation" — so the command ends `<$TTY >$TTY 2>&1`: the shell's own terminal device, since `claude` (Bun) dies on `/dev/tty` itself, which macOS's kqueue won't watch (`EINVAL: invalid argument, kqueue`). The command is named after the session's config dir, dot and dashes dropped: `claude` for `~/.claude`, `claudek` for `~/.claude-k`. That is the alias which starts the other profile, and it sets more than `CLAUDE_CONFIG_DIR` (endpoint, token, CA certs), so a new profile needs an alias named this way to be resumed. A `claude` suspended with Ctrl+Z isn't among the window's `foreground_processes` (kitty lists only the shell), so failing that the window's claude is the one `ps` shows as a child of its shell (`.pid` in `kitty @ ls`). Any other window that was in the middle of a command when saved (`at_prompt` false in `kitty @ ls`) comes back with that command typed at its prompt and not run — `print -z`, zsh's way of putting text in the editing buffer, as its `cmd_at_shell_startup` — so a dev server (`pnpm dev`) is one Enter away and the window says what it was for. The text is `last_reported_cmdline`, the command line as typed, which kitty's shell integration reports; the foreground process's arguments would lose aliases, pipes and variables (`pnpm dev` is a `node` process). A pager is run rather than typed, since that is safe: a command line starting `less`, `more`, `most`, `bat` or `man` with no pipe, redirection, substitution or second command in it. The window `save-session` was typed in is left alone. The command line is single-quoted for the shell, and its quotes are then written as `\u0027` in the JSON, which sits inside a single-quoted word of the session file. `--resume` by id rather than `claude -c`, which would give two agents in one directory the same conversation. kitty's `--use-foreground-process` isn't used: it re-runs whatever any window was running. Also dropped: the overlay `save-session` itself runs in when launched from a key binding, and the `seen_at`/`agent_state` user vars, which kitty would otherwise restore stale. Tested in `window-tests.zsh`.

**`bin/next-agent`** — no picker: focuses a window whose Claude agent needs you. The states are the `agent_state` user var that `kitty/focus_watcher.py` publishes (from the window's Program Status Protocol records, kitty 0.50+), with `agent_state_at` saying when it last changed. Ranking is blocked, then error, then done, the most recent change first within each; it picks the one after the current window in that order (wrapping), so repeated presses cycle through them all. When none needs you — or only the window you're in does — it goes to the most recently focused other `claude` window (by `last_focused_at`), so the key toggles between two agents; it does nothing only when there is no other one. Windows with no agent state are never ranked, but the toggle can still reach them. `--prev` steps backwards through whichever list applies (the least recently focused, when nothing needs you). Bound as `map kitty_mod+j launch --type=overlay --cwd=current next-agent` and `map kitty_mod+shift+j launch --type=overlay --cwd=current next-agent --prev`, like the pickers — not `--type=background`: kitty puts `KITTY_LISTEN_ON` in the environment of processes running in its windows only, so a background launch's `kitty @ ls` fails and the key silently does nothing. The current window is the one the overlay covers (`state:overlay_parent`, as in `bin/window`); run from a shell instead, it's the active window of the active tab of the focused OS window (`is_focused` alone is true for the active window of *every* tab).

**`bin/tidy-windows`** — reviews every open kitty window and recommends **close** (stale/safe to discard), **move** (consolidate onto its project's tab — one tab per project), or **keep**, in an `fzf --multi` picker; nothing is applied until confirmed. The interactive picker only lists close/move rows (`to_fzf_tsv` drops "keep" — selecting one there would be a no-op) and pre-selects all of them on load (`--bind 'load:select-all'`, fzf's documented idiom for this — opt-out: Tab deselects one you disagree with, Enter applies the rest). `--dry-run` shows the full picture instead, including keeps and why (e.g. the current-window protection below). Prints a status line to stderr immediately on launch and `advise` prints its own progress (window/git scan, then the API call) so the screen is never blank while waiting on the model. `advise` also prints why on stderr when there's nothing to do (no open windows, or everything reviewed and kept) — since this is an overlay that vanishes the instant the script exits (taking anything printed to it along), `bin/tidy-windows` blocks on a keypress in that case, and again at the end if any close/move failed or was refused, so the message is actually seen rather than flashing and disappearing; a clean close/move needs no pause, since the windows themselves are the visible confirmation. Bound in `kitty.conf` as `map kitty_mod+shift+w launch --type=overlay --cwd=current tidy-windows`, alongside `switch-project`'s and `window`'s overlay bindings — see "Kitty key bindings" in `CLAUDE.md`. Finds the real current window the same way `bin/window` does (`kitty @ ls --match 'state:overlay_parent'`) and passes its id to `advise` as `--current-window-id`, plus keeps its own defense-in-depth check that refuses to close/move that id even if selected. Thin zsh glue otherwise: fetches `kitty @ ls`, pipes it to `../python/tidy-windows-advise/advise` (resolved via `${0:A:h}`, same pattern `bin/switch-project` uses for `project.zsh`), then applies the returned `id / action / target_tab` TSV rows via `kitty @ close-window` / `kitty @ detach-window --target-tab` (the same primitive `bin/switch-project` uses for moving a window to a tab), reporting any failed close/move rather than swallowing the error. All judgement logic lives in the Python script — see below.

**`../python/tidy-windows-advise/advise`** — a `uv run --script` executable (inline PEP 723 deps, no separate venv setup needed) that owns all of `tidy-windows`'s logic: parses `kitty @ ls` JSON, computes idle time (from the window's `seen_at` user var when `kitty/focus_watcher.py` has stamped one; otherwise from `kitty @ ls`'s `last_focused_at`, which is on kitty's monotonic clock — not wall-clock, and on macOS it stops during sleep, so it is only compared with the newest `last_focused_at` of any window, standing in for "now"; an unqualified `"idle"` label if neither is available), enriches each window with `git` state (branch, dirty, ahead/behind upstream, last-commit recency) via `git -C <cwd>` and, when the window is running `claude`, its Claude Code session name (see "Claude session names" below), and asks the Claude API (`ANTHROPIC_API_KEY`, model `${TIDY_WINDOWS_MODEL:-claude-haiku-4-5-20251001}`, structured `output_config: json_schema` output) to judge close-vs-keep — a distinctive session name is a signal toward "keep". `kitty @ ls`'s `is_focused` is per-tab (the last-active window *within that tab*), not "the window the user is looking at right now" — several tabs can each show `is_focused: true` simultaneously, and the actual current window (the one under the `tidy-windows` overlay) reads `is_focused: false` at the moment `kitty @ ls` runs, since kitty treats the overlay as that tab's active window while it's open. Its idle label is worded "active in tab" rather than "focused now" so it can't be mistaken for `protect_current_window`'s unambiguous "YOU ARE HERE" marker. So the system prompt treats `is_focused` as only a weak signal, and `protect_current_window` hard-overrides the row matching `--current-window-id` (supplied by `bin/tidy-windows`, found independently via `state:overlay_parent`) to `keep` regardless of what the model said — the one window that must never be touched isn't left to the model's judgement. The model is sent every foreground process's command line (`processes`), not just the first — a dev server's first is often a helper such as `esbuild` — and asked never to close a window where one looks like a long-running server/watch/daemon. It has done so anyway, so `protect_running_processes` hard-overrides `close` to `keep` for any window running something other than a shell prompt (`running_commands`: the foreground processes' basenames minus shells and `fzf` — a picker left open holds nothing, so a stale one can be closed; empty for a `claude` window, whose agent state decides instead), and the row's label names what is running, e.g. `(esbuild, node)`. So only windows sitting at a shell prompt, showing a forgotten picker, or with an idle Claude session, can ever be recommended for closing. An overlay window (any id but the lowest in one of its tab's `groups` in `kitty @ ls` — kitty doesn't list a group base-first, but an overlay is always newer than the window it covers) is the one case decided without the model: other than the overlay `tidy-windows` itself runs in, which is `is_self` and never listed, an open overlay is one you walked away from, and closing it only reveals the window underneath — so `merge_actions` always recommends `close` for it, labels it `(overlay)`, and the running-process rule doesn't apply (an active Claude agent in one is still kept). Move recommendations are **not** AI-judged — `plan_moves` deterministically groups windows by project (the git root — for a linked worktree, the main worktree's root, `git_summary`'s `project_root`: a worktree is a branch of its repo, not a project of its own) and moves each window onto its project's tab. A tab's name is the last component of its title (`tab_name`: `switch-project` titles a tab with the bare project name, while an untitled tab shows its window's title, a path). A tab is *owned* by the project it is named for, or else the one with strictly the most windows in it; a project's home is a tab it owns — a titled one first, then the one with most of its windows. A window not on its home moves there. A project with no home whose window sits in a tab another project owns gets a target of `new:<project>`: `bin/tidy-windows` sends each of the project's windows to the tab titled with the project name (`detach-window --target-tab=@title --tab-title=<project> --location=by-title --create-if-missing`), which kitty makes in alphabetical place for the first and the rest join. A tab nobody owns (a tie, untitled) is left alone. A planned move survives a `close` that `protect_active_agents` or `protect_running_processes` turns into a keep (`planned_move` on the row) — such a window is exactly the kind that is left in the wrong tab. `zsh/functions/project.zsh`'s `_project_tab_name` gives the same name (the main worktree's directory name) to the tabs `switch-project` and `window` make. Falls back to an all-`keep` table (keeping the deterministic moves) if the API call fails for any reason, so `tidy-windows` still works without a key. A window running `claude` also carries its agent state (`claude_state`: blocked, working, done or idle — see "Claude session state" below; `agent_state`/`claude_agent_state` mirror the zsh rules, reading `seen_at` from the window's user vars and treating `--current-window-id` as the window being looked at). The model is told what the states mean, a blocked, done or working row's label gets the picker's `!`, `✓` or `…`, and `protect_active_agents` hard-overrides any `close` on a window running `claude`, in any state, to `keep` (closing it would kill the task or discard an unread answer, and even an idle session is a conversation of its own) — moves stand, since the session carries on in its new tab. The prompt also says that two `claude` windows in one directory are never duplicates of each other; the duplicate rule is for shell windows. Follows the `anthropic` SDK + `uv run --script` + `output_config: json_schema` pattern from the sibling `organise-inbox` repo's `skills/organise-notes/scripts/classify_note_api`. Tested with `pytest` (`tests/test_advise.py`) — real scratch git repos for `git_summary`, mocked Anthropic client for `advise`, no live kitty/network calls.

## Claude session names

Claude Code writes `<config-dir>/sessions/<pid>.json` (undocumented internal state — `pid` is the `claude` process's own pid; `<config-dir>` is normally `~/.claude`, but a process started with `CLAUDE_CONFIG_DIR` set, e.g. for a separate work profile, uses that dir instead — this machine also has `~/.claude-k`) for each active session, and separately appends `{"type":"ai-title","aiTitle":"..."}` lines to that session's own transcript as a human-facing title gets generated/regenerated over the conversation. `zsh/functions/claude-session.zsh`'s `_claude_session_title` (jq, keyed by `foreground_processes[-1].pid`; sourced by `bin/window-list`) looks up a window's title this way: search every `~/.claude*` directory that has a `sessions/` subfolder for `sessions/<pid>.json` (checking only `~/.claude` was an earlier bug — a window running under a different config dir showed no title at all), read its `sessionId` (and its `"name"` field as a fallback), find `<that config-dir>/projects/*/<sessionId>.jsonl` by `find` — not by reconstructing the project-slug directory name from `cwd`, since that slug transform is lossy (e.g. `.` becomes `-` too, not just `/`) and not worth depending on — and take the last `ai-title` line in it. session.json's own `"name"` field (e.g. `"project-tools-8f"`) is *not* this title — it's a short slug derived at startup for use as an addressable session name elsewhere, and looks superficially plausible enough that it was mistakenly treated as the display title in an earlier version of this feature. It's used only as a fallback when no `ai-title` has been recorded yet (e.g. a very new session). A missing/malformed session file, or no transcript found, means "no title available" rather than an error, since this is unstable internal state that could change between Claude Code versions. Shown in faded grey, in place of the process name.

An interactive session can also delegate to and "park" on a background job — a separate `claude` process with its own pid and `sessions/<pid>.json` (`"kind":"bg"`), linked back from the interactive session's file via `"parkedJobId"` matching the job's own `"jobId"`. While parked, the interactive session's own transcript typically has no `ai-title` yet (nothing's been said in it since the job started), so without special handling its window would show the interactive session's bare derived slug (e.g. `"context-e1"`) even though the parked job's own `"name"` (e.g. `"sources/ publishing design"`) is the descriptive title actually visible in that terminal. So the lookup is recursive (`_claude_session_title_from_file`): prefer a session's own `ai-title`; failing that, if it's parked, follow `parkedJobId` to the job's session file (scanning sibling session files in the same config dir for a matching `"jobId"`) and resolve *its* title by the same rule; failing that, fall back to the session's own `"name"` slug.

Session files are never deleted when the `claude` process exits, so a pid can later be reused by an unrelated process — a join on pid alone would then attach a stale title to whatever now happens to be running in that window. `bin/window-list` guards against this the same way its own process-name fallback already identifies a claude window: kitty's live `foreground_processes[-1].cmdline[0]`. The title lookup only runs when that window's current foreground process actually is `claude` right now; otherwise it falls through to the process name, same as if no session file existed at all. (A pid reused by a *new* claude process needs no such guard — that process overwrites its own session file with fresh data the moment it starts, so the join is naturally correct.) An earlier attempt at this guard compared the session file's recorded process-start time against the live process's `ps -o lstart=` — it was strictly worse: fragile across BSD/GNU `date` on `PATH` and locale, and broke matching entirely in practice.

**The `agent_title` user var comes first.** `kitty/focus_watcher.py` publishes each `claude` window's session name as its `agent_title` user var (`kitten @ ls` shows it under `user_vars`): a name you gave the session yourself (`/rename`; the session file's `"name"` with `"nameSource": "user"`), else its last `ai-title`, else a parked job's — never the startup slug. `bin/window-list` (`_window_list_name`'s `AGENT_TITLE` argument), `bin/sw-preview` and `advise` (`build_rows`' `agent_title`, ahead of `claude_session_name`) use it when it is there, so a name you gave a session shows in the window picker, the project preview and `tidy-windows` as it does on the tab. With no `agent_title` the `agent_hint` var comes next — a quote of what was last asked, `“…`, cut to the picker's name column — which is how three untitled `claude` windows in one project tell each other apart (in `advise` the model is told a quoted one is not a name). A window with neither var — one the watcher has not seen, or a session with no prompt yet — falls back to the lookup above, slug included, as before; and, as with the lookup, the var is only read for a window whose foreground process is `claude` right now, so one left on a window that has since stopped running it is ignored. The lookup above does not know of `nameSource`, so without the var a name you gave a session is not shown, only its `ai-title`.

`python/tidy-windows-advise/advise`'s `claude_session_name()` mirrors all of the above (ai-title lookup, config-dir search, parked-job fallback) — see its own doc comment for the Python-side details. It gets its staleness guard the same way `bin/window-list` does: `build_windows_payload` only calls it when the row's `proc` (the frontmost foreground process's cmdline basename, from `build_rows`) is `"claude"`.

## Claude session state

The same `sessions/<pid>.json` carries `"status"` (`busy`, `shell`, `idle` or `waiting`, with `"waitingFor"` saying why) and `"statusUpdatedAt"` (ms epoch, written only when the status changes — an idle session's stays put for hours, which is what makes "done" below possible). `_claude_session_state PID SEEN_AT IS_CURRENT` in `zsh/functions/claude-session.zsh` turns that into the herdr-style states `bin/window-list` uses, printing `STATE<TAB>SINCE` (epoch seconds of the status change):

| State | Rule |
|---|---|
| `blocked` | `status` is `waiting` (a permission prompt or a question) |
| `working` | `status` is `busy` |
| `done` | `idle` or `shell`, and it got there after you last looked at the window |
| `idle` | any other `idle` or `shell` |

`shell` isn't documented. It was first taken for "running a shell command" and shown as working, but a session sits in it after its turn has finished — seemingly while a shell command it started is still running in the background — so it counts as idle.

Anything else (no session file, malformed, a status this doesn't know) is no state at all, and the same live-`claude` guard as for titles applies — callers only ask when the window's foreground process is `claude` right now.

"Last looked" can't come from kitty's own `last_focused_at`: that records only when a window *gained* focus, so an agent that finished while you watched would count as unseen the moment you left. Instead **`kitty/focus_watcher.py`**, a global watcher (`watcher focus_watcher.py` in `kitty.conf`), sets a `seen_at` user var (wall-clock epoch seconds) on each window on focus gain *and* loss; it comes back in `kitty @ ls` as `.user_vars.seen_at` and goes away with the window. A window with no `seen_at` — created before the watcher was configured; kitty only attaches global watchers to new windows — is never `done`, just `idle`. Nor is the window you're in (`$WINDOW_CURRENT_ID`, exported by `bin/window` so fzf's reloads of `window-list` inherit it).

`window-list` passes `seen_at` through its tab-separated rows as `-` when absent: tab is IFS whitespace, so `read` would swallow an empty field and shift the rest.

### Tab markers and notifications

The same states also show without asking. `kitty/focus_watcher.py` doesn't only stamp `seen_at`: every 2 seconds (`add_timer`, started from the watcher's `on_load`) it works out the state of every window whose foreground process is `claude`, by the rules above (`agent_state` in the watcher mirrors `_claude_session_state` — keep the two in step), and publishes it as the window's `agent_state` user var, removing the var when there's no state. It also stamps `agent_state_at` (epoch seconds) whenever the published state changes, which `bin/next-agent` orders by. A focus change refreshes that one window at once, so a `done` clears as you arrive. Polling rather than Claude Code hooks: it's the picker's own source of truth, so the two can't disagree; it sees what no hook fires for (an Esc interrupt, a question prompt); it needs nothing in any profile's Claude settings; and the cost is a few small file reads, for a lag of up to 2s.

Where the window reports its own state, the watcher uses that instead of the session file. Claude Code 2.1.295 and later send their state through the Program Status Protocol (OSC 7501) when the terminal answers its startup query, and kitty 0.50 answers and keeps the records on `window.program_status` (also `program_status` in `kitten @ ls`). `status_state` takes the most pressing of the window's `claude-code` records (`blocked`, then `error`, `done`, `working`, `idle`; `error` exists only on this path, the session file has no such state) and ignores their `msg` and `title`, which can hold commands and paths. kitty keeps a `done` until you focus the window or press a key, so a `✓` needs no `seen_at`; a `done` arriving in the window you are looking at is shown (until your next key press) but doesn't notify. The watcher's `on_program_status_change` publishes it at once, with none of the 2s lag. A window with no `claude-code` record — an older Claude Code, a terminal that didn't answer the query, or an idle record kitty dropped at the next prompt — falls back to the session-file rules above, so those still need `seen_at`. `window.program_status` is kitty-internal, not documented API: if a kitty update drops or renames it, every window just falls back. Design and verification notes: `docs/superpowers/specs/2026-11-04-program-status-agent-state-design.md`.

When a window's state changes, the watcher:

- marks that OS window's tab bar dirty, and **`kitty/tab_bar.py`**'s `draw_title` — kitty calls it for `{custom}` in `tab_title_template` — gives each tab one marker for the most pressing state among its windows: red `!` blocked, else red `✗` error, else green `✓` done, else yellow `…` working, in bold; nothing otherwise. The marker is on the tab's second line (below), with the title of that agent's Claude session. `draw_title` also draws kitty's activity symbol (`tab_activity_symbol`) before the title, but only for windows with no `agent_state`: Claude Code repaints when it loses focus, which kitty counts as activity, so a tab of agents would always show it. And it draws the title (so the template has `{custom}` in place of `{activity_symbol}` and `{title}`), and shortens one that is a path, fish style: the last directory whole, the two above it cut to their first letter, any further up dropped — `github.com/garethrowlands/project-tools` is `g/g/project-tools`, `/Users/gareth/worktrees/project-tools/fix-tabs` is `…/w/p/fix-tabs`, with the `…/` halfway between the tab's text and background colours so it doesn't read as the working marker. Only the tab bar changes; window titles keep the full path.

  **Vertical tab bar, status lines.** `kitty.conf` has `tab_bar_edge left`, `tab_bar_style separator`, `tab_title_max_length 20` and `tab_title_max_lines 6` (the powerline style draws each of a tab's lines with its own rounded caps, and `fade` draws pixelated edges, so neither suits several lines). A newline in what `draw_title` returns starts another line (in a horizontal bar kitty drops everything after the first). Under the title there is a line for each agent in the tab, the most pressing first (blocked, error, done, working, idle; of equals, the most recently changed): its own marker (blank for an idle agent, as in the window picker), then its Claude session title (`agent_title`); until the session has a title, a quote of what was last asked in it (`agent_hint`, `“which service owns the invoice?`); just the marker if it has neither, and `claude` for an idle agent with neither. Every line under the title is in the same faded grey (the markers keep their colours), and has the marker's cell: a marker is one cell wide whatever the state, and a line without one has a blank there, so the text starts in the same column on every line. After the agents, a line for each window that isn't an agent: the command running in it (`last_cmd_cmdline` while `at_prompt` is false, else the foreground process's name), and for a shell at a prompt the shell's (`zsh`) — the tab bar and the window picker list the same windows. Commands come first, the active window's first, then the shells. kitty draws the tab on a title change, before it has been told the command, and not again when the command ends, so the watcher's poll redraws the tab bar when a window's `at_prompt` or `last_cmd_cmdline` changes (`refresh_program`). With more than fit, the last line says how many more (`+3 more`); with `tab_title_max_lines 2` there is one line, the most pressing agent's, with `+N` for the other agents. A tab with no windows to show stays a single line. **Horizontal bar, or none.** shift+option+t (`bin/tab-bar`, bound through `action_alias tab_bar_cycle …` so that the command palette shows `tab_bar_cycle`) moves the running kitty left → bottom → none → left: `kitten @ load-config -o tab_bar_edge=bottom -o tab_bar_style=powerline -o tab_title_max_lines=1 -o tab_title_max_length=0` for a horizontal bar, `-o tab_bar_style=hidden` for none (both overrides, which survive later reloads), and `--ignore-overrides` (then a plain reload: after none the first doesn't bring the bar back) to return to the left, so `kitty.conf` doesn't change and a restart is vertical. `tab-bar vertical|horizontal|none` names one. kitty can't say which it is in, so the script keeps the mode in `~/.cache/project-tools/tab-bar-mode` beside kitty's pid (`$KITTY_PID`). kitty drops everything after the first line of a title in a horizontal bar, so there `tab_bar.py` (`vertical()`) puts the most pressing agent's marker in front of the title and draws no lines. The alias is `launch --type=background --copy-env tab-bar toggle`: a background launch has no `KITTY_LISTEN_ON` of its own. `load-config` does not re-read the theme from `dark-theme.auto.conf` (kitty applies that on start and when the OS appearance changes), so after a switch in a kitty that was started before a theme file change the colours are the old ones until `kitten @ set-colors --all --configured kitty/themes/catppuccin-mocha-crust.conf`. A line longer than the bar is cut with `…` by `tab_bar.py` itself, to leave room for the marker's cell: kitty's own cut keeps a stray last character. **`agent_title`** is published by `focus_watcher.py` next to `agent_state`: the last `ai-title` of the session's transcript (read incrementally, since a transcript only grows), else a parked job's, else nothing — not the session's `name` slug that the window picker falls back to, since `context-37` on a tab says nothing. It is the third copy of the title lookup (after `claude-session.zsh` and `advise`); keep them in step. **`agent_hint`** is published beside it, only while there is no title: the last `{"type":"last-prompt","lastPrompt":...}` record of the session's transcript, which Claude Code writes for each prompt you type. `last_prompt` reads only the end of the transcript (64 KB, doubling up to 4 MB, and again only when its size changes), collapses it to one line, cuts it to 100 characters, and passes over commands (`/clear`, `<command-name>` entries) and, for a prompt shorter than `HINT_MIN_LENGTH` (12), a reply like "yes" that says nothing about the session: it takes the previous prompt, or the short one if that is all there is. Like the rest of the transcript, that record is undocumented Claude Code internals.
- if it became `blocked`, `error` or `done` in a window you aren't looking at (not the active window of the focused OS window — which includes kitty not being frontmost at all), sends a desktop notification through kitty's notification manager: "Claude needs you", "Claude failed" or "Claude finished", with `<tab title> › <cwd basename>`. Clicking it focuses the window. One per change, never repeated while the state holds. Claude Code's own notifications are separate; if both fire for a permission prompt, turn its channel off in `/config`.

Unlike `seen_at`, the poll covers every window, including ones older than the watcher (kitty loads a watcher file once and caches it by path, and its focus events only reach windows created after that; to pick up a changed watcher without restarting kitty, symlink it under a new name, point `watcher` at that and reload the config — the new copy's `retire_older_copies` then silences the old one's poll, which kitty would otherwise keep running beside it) — those just never show `done`.

If two config dirs each have a `sessions/<pid>.json` for the same pid (one left by a dead process whose pid was reused under the other profile), both the zsh and the watcher lookups take the most recently modified.

## zoxide ranking

The `fd` scan cache stays the source of truth for projects; zoxide only adds to it and orders it. Rules applied in `_project_build_list`'s awk:

- **Discovery** — a zoxide `repo` dir missing from the cache (i.e. outside `PROJECT_ROOTS`, e.g. `~/claude_certification`) is added, labelled with its `~`-abbreviated absolute path. A worktree's main repo is added the same way. Worktrees, submodules and non-git dirs (`/`, `~/gitlab.kfplc.com`, …) are never listed as projects. This is done per picker launch, not in the cache, since zoxide changes constantly and the cache only refreshes on `--refresh`.
- **Roll-up** — each zoxide score is credited to the innermost repo containing that dir (walking up the path), with a worktree counting as its main repo. So time in `context/src/foo` or in a sibling `order-sourcing-service-worktrees/rod-plan` ranks `context` / `order-sourcing-service`. Scores for dirs outside any repo are dropped.
- **Open detection** uses the same walk-up, so a kitty window in a worktree marks its main project *Open*. It marks every enclosing repo (not just the innermost), preserving the earlier prefix-match behaviour for nested repos. Worktrees zoxide has never seen can't be mapped without a `git` call per cwd, so a window in one of those doesn't count — worktree drill-down is tracked as beads `pt-bun.6`.
- `fd --type d --glob .git` never matched worktrees anyway (their `.git` is a file), so they weren't listed before this either.
- `zoxide query` also tries to age its database on every query; a failed write (e.g. in a sandbox) still prints results, so stderr is discarded.

## Conventions

- `_project_build_list` uses BSD awk with roots, CWDs and zoxide scores fed via process substitution (separated by `---` sentinels) to avoid newline-in-`-v` issues. BSD awk has no `asort`, so it emits `GROUP<TAB>SCORE<TAB>LABEL<TAB>PATH` rows, pipes them through `LC_ALL=C sort`, and a second awk adds the group headers.
- `kitty @ ls` JSON is pre-fetched once at picker startup and written to a temp file; preview subprocesses read the file rather than calling `kitty @`. With tty-based remote control (no `listen_on`), `kitty @` blocks in subprocesses; with `listen_on` configured (socket-based), `KITTY_LISTEN_ON` is inherited and `kitty @` works in subprocesses — `bin/window` relies on this for its live preview.
- `null` CWDs in kitty ls JSON are guarded with `// empty` before `startswith()` to avoid jq type errors.
- `FZF_PREVIEW_COLUMNS` (not `$COLUMNS`) is used for preview pane width — fzf sets it in the preview subprocess.

## `sw` — worktree / branch switcher

**`functions/sw.zsh`** — source this to get `sw`, an fzf picker over the current repo's worktrees and local branches. Worktrees (`⎇`) come first, then branches with no worktree, each group most-recently-committed first; `*` marks the current checkout. Paths are shown short: `(main worktree)` for the main worktree (the original clone, which holds the real `.git` dir), relative to it for worktrees inside it (e.g. `.claude/worktrees/fix-foo`), `../name` for siblings, else `~`-abbreviated. Picking a worktree `cd`s there; picking a plain branch runs `git switch` in the current worktree — or, with **ctrl-o**, checks it out in a new sibling worktree and `cd`s there (a header line shows the keys). **ctrl-i** opens the highlighted worktree in its IDE (`bin/ide`, as in the project picker) and leaves `sw` open; on a branch without a worktree it opens the main worktree. The new worktree goes beside the main one as `<repo>-<branch>`, dropping a leading prefix segment (`feat/`, `fix/`, …) and turning other `/`s into `-` (`_sw_worktree_path`: `context` + `feat/unit-inventory-file` → `../context-unit-inventory-file`); if that folder already exists `sw` errors rather than reuse it. ctrl-o on a branch that already has a worktree just `cd`s there, since git allows a branch in only one worktree at a time. It must be a sourced function, not a `bin/` script, since it `cd`s the calling shell. `_sw_list` builds the rows (`PATH<TAB>BRANCH<TAB>DISPLAY`) from `git for-each-ref`'s `%(worktreepath)` plus detached worktrees from `git worktree list --porcelain`.

**`bin/sw-preview`** — `sw`'s fzf preview (right-hand pane), a script because fzf runs previews in a fresh shell; `sw.zsh` finds it relative to itself, so it needs no symlink. For the highlighted row it shows:

- a header: the branch, how far ahead of and behind the default branch it is, and its last commit's age. The default branch is the local one named by `origin/HEAD`, else `main`, else `master`.
- **Windows** (worktrees only): the kitty windows whose cwd is in that worktree — tab title, then a `claude` window's agent-state marker as in the `window` picker and its conversation title as a `[title]` tag, or `(proc)` for anything else; the window `sw` was run from is tagged `this window`. Worktrees nest (one under `.claude/worktrees` is inside the main one), so a window counts for the deepest worktree containing its cwd. The section is left out when kitty can't be reached (outside kitty, or no `listen_on`).
- **Uncommitted** (worktrees only): `git status --short`, capped at 12 lines, or `clean`.
- **Last commit**: the newest commit's hash, author and full message (capped at 16 lines).
- **Not on main**: up to ten of its commits that aren't on the default branch, then their `git diff --stat`; `No commits beyond main` if there are none (merged, or not started); for the default branch itself, its recent commits.
